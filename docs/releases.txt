Manual releases

The Release workflow (.github/workflows/release.yml) builds the master commit
selected at dispatch time. It publishes one Android ARM64 APK and one macOS
ARM64 DMG, plus SHA256SUMS. The Android APK is signed with the Android Secrets.
The manual release requires macOS signing Secrets before starting the builds.
Both a local self-signed certificate and an Apple Developer ID certificate are
supported. Other shared-workflow callers can still build an unsigned DMG.
See docs/macos-signing.txt for setup, Secrets, and stable update identities.
Android signing keys cannot sign macOS applications.

Setup
In repository Settings > Secrets and variables > Actions, create:
  ANDROID_SIGNING_KEY         Base64 of the complete release keystore
  ANDROID_ALIAS               alias of its private key (rustdesk-release)
  ANDROID_KEY_STORE_PASSWORD  keystore password
  ANDROID_KEY_PASSWORD        private key password (same password for PKCS#12)

Use the same keystore for future releases and keep a backup with its password.
Keystores, passwords and their Base64 exports belong outside the repository.
The local setup uses ../.toolchains/signing/android beside the checkout:
  rustdesk-release.p12        password-protected PKCS#12, RSA 4096
  keystore-base64.txt         value for ANDROID_SIGNING_KEY
  key-alias.txt               value for ANDROID_ALIAS
  keystore-password.txt       value for both password secrets
  certificate-sha256.txt      public certificate fingerprint
No signing material is uploaded by local tooling automatically.

Run
The workflow must first be merged into the repository's default branch so that
GitHub displays its Run workflow button. Open Actions > Release > Run workflow,
select master, enter the version without v (X.Y.Z or X.Y.Z-N) and an Android
versionCode greater than every previously released base build number. Choose
whether this is a prerelease. Runs against other branches are rejected.

VersionName is the supplied version. Flutter adds +2000 to the supplied base
versionCode for the ARM64 split APK. Continue using this APK variant for updates.
The base code must also exceed the number in pubspec.yaml; leave room for the
largest ABI offset below Android's 2100000000 limit.

Version stamping changes Cargo.toml, the root Cargo.lock package and pubspec.yaml
only inside CI's disposable checkout. It does not commit generated version edits.
The vVERSION tag points to the exact master source commit used for the build.
An existing tag is never moved or reused. After all builds and signature/version
checks pass, the workflow creates the tag and a draft release, uploads both
assets and the checksums, then publishes it. If publication fails, inspect the draft
release/tag before choosing a new version; reruns do not overwrite an existing tag.
Missing Android signing secrets fail the build; the manual workflow has no
unsigned Android release fallback. Tags created using GITHUB_TOKEN do not
trigger Flutter Tag Build.

The application ID is com.carriez.flutter_hbb. This release key differs from the
official RustDesk key and from a local debug key: the first installation cannot
update an APK signed by either of those keys. Export settings before replacing
such an installation. Subsequent releases signed with this key can update it.

Validation and regression surface
  python3 -m unittest discover -s .github/scripts -p test_android_release.py
  actionlint .github/workflows/release.yml .github/workflows/flutter-build.yml
The shared workflow already contains a legacy `if: False` lint diagnostic in its
disabled web job; it is unrelated to this release workflow.

Build scope and regression surface
Existing runtime/app code is unchanged. The shared flutter-build.yml defaults to
platforms: macos-android-arm64 for Release, Full Flutter CI, Tag and Nightly.
Only aarch64-apple-darwin and aarch64-linux-android app builds run. Other platform
jobs and matrix entries are retained; setting platforms: all in a caller restores
those upstream targets. The Android-only profile remains available as android.

bridge.yml prepares the common bridge once on Ubuntu, using Flutter 3.22.3.
This is a build prerequisite, not a Linux application. The additional Flutter
3.44 bridge is generated only when platforms: all enables Windows ARM64.
ci.yml retains its standalone Linux job but runs it only when the repository
variable ENABLE_LEGACY_LINUX_CI is explicitly true. flutter-nightly.yml keeps
manual dispatch; its daily schedule is commented out to save runner minutes.
flutter-ci.yml also keeps manual dispatch; its push/PR triggers are commented out.
checks.yml replaces automatic builds with one Ubuntu job capped at five minutes:
release version tests, existing update-signature/CLI tests, and pinned actionlint
with a verified download checksum. It needs neither submodules nor Rust, Flutter,
Android SDK or signing Secrets. Superseded checks are cancelled automatically.
These checks do not compile application code. Dart, Kotlin and Rust tests remain
in the manually dispatched Full Flutter CI build for the two ARM64 targets.

release.yml collects just the ARM64 APK and DMG and publishes them together.
The shared macOS job stamps the requested release version and uploads its final
DMG after optional signing; deferred publication prevents an early release.
No release or paid build is started automatically by the release workflow.
