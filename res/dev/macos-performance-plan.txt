macOS: план следующего этапа после Android
Дата: 2026-10-24. Это план, не реализованная системная функция.

Подтверждено по текущему коду
- У установленного RustDesk есть root LaunchDaemon: service из app bundle,
  src/service.rs -> platform::macos::start_os_service() -> IPC _service.
  Установка/обновление службы требует административного подтверждения,
  а последующая работа службы не требует sudo на каждом подключении.
- Код находится в src/platform/macos.rs и src/platform/privileges_scripts/.
  В текущей установке LaunchDaemon присутствует и работает (проверен launchctl).
- Защищённый канал _service сейчас допускает только SyncConfig. Ослаблять
  этот список и принимать произвольные shell-команды для AWDL не требуется.
- Уже есть ipc::connect_for_uid(), который на macOS проверяет UID/PID и
  executable установленного пользовательского --server процесса.
- VideoConnCount(None) возвращает число авторизованных Remote-подключений;
  файловые/терминальные сеансы сюда не входят. Считать TCP-сокеты вместо
  авторизованных сеансов нельзя: аутентификация, relay и reconnect отличаются.

Этап 1. Настройка AWDL на время входящих видеосеансов
1. Добавить выключенную по умолчанию настройку только для macOS. Текст должен
   прямо объяснять, что использующие AWDL функции AirDrop/Continuity будут
   временно недоступны. Обычный клиент без установленной/подходящей службы
   должен объяснять необходимость её установки/обновления.
2. Реализацию поместить в отдельный src/platform/macos/awdl.rs; общие файлы
   получают минимальные cfg(macos)-хуки. Настройку можно синхронизировать
   существующим SyncConfig, без нового публичного административного RPC.
3. Root-служба получает состояние установленного --server через проверенный
   user IPC: число авторизованных Remote-сеансов и настройку. Примерный период
   проверки 1 с; запросы ограничены timeout и не блокируют видеопоток.
4. При первом активном сеансе сохранить исходное состояние awdl0. Если он был
   UP, выполнить только фиксированную команду /sbin/ifconfig awdl0 down.
   Никаких команд, имён интерфейсов или аргументов от удалённого клиента.
5. Пока есть хотя бы один входящий Remote-сеанс, режим остаётся активным.
   Закрытие одного из нескольких клиентов не должно преждевременно возвращать
   AWDL. Окончание последнего сеанса или выключение настройки возвращает
   исходное состояние. Если AWDL уже был DOWN, RustDesk не включает его сам.
6. Потеря пользовательского --server, logout, остановка/обновление службы
   должны освобождать режим. Для падения root-службы нужен механизм recovery
   её собственного изменения состояния (например, небольшой root-owned
   журнал в /var/run с восстановлением при следующем старте). Конкретный
   механизм выбрать до реализации после проверки launchd shutdown/restart;
   нельзя оставлять интерфейс выключенным при прекращении RustDesk.
7. Политику на случай, если macOS сама возвращает AWDL UP во время сеанса,
   проверить на этом Mac. Не добавлять бесконечный частый цикл переключения.
   Ошибки должны быть видны пользователю и в ограниченном по частоте логе.

Проверки этапа 1
- Настройка выключена: системный интерфейс не меняется.
- Один/два клиента: down на первом, up после последнего; перенос reconnect.
- Изначально выключенный AWDL остаётся выключенным после сеанса.
- Выключение настройки, аварийное завершение --server/root service,
  остановка/обновление службы и смена пользователя восстанавливают состояние.
- Файловая передача/терминал и неавторизованное подключение не включают режим.
- Реальные Wi-Fi A/B-замеры: FPS, p95/p99 и длинные паузы, не только средний FPS.
  Перед каждым замером пользователь открывает и подтверждает анимацию.

Этап 2. Захват и кодирование macOS-хоста
FastRustDesk — действительно пример оптимизации хоста, который отдаёт экран:
https://github.com/JoshuaHKU/FastRustDesk
https://github.com/JoshuaHKU/FastRustDesk/blob/main/FastRustDesk.md
Автор описывает ScreenCaptureKit вместо CGDisplayStream, захват NV12 и
передачу IOSurface/CVPixelBuffer прямо в VideoToolbox, чтобы убрать CPU
преобразование BGRA и полнокадровые копирования. Его цифры CPU относятся
к его тестам; в перечне оптимизаций есть снижение capture cap 60 -> 30 FPS.
Этот предел нам не подходит: целевой режим этого проекта — 60 FPS.

Текущий feature screencapturekit в нашем Cargo.toml включает аудио CPAL,
а сам экран захватывается кодом libs/scrap/src/quartz/ на CGDisplayStream.
Нельзя считать включение этого Cargo feature готовой миграцией экрана на SCK.

Порядок работ
1. Подготовить macOS toolchain по CI (включая MAC_RUST_VERSION=1.81 и
   arm64-osx vcpkg-зависимости). Android toolchain не заменяет macOS-сборку.
   Снять baseline именно Mac-хоста: capture/encode FPS, интервалы, CPU и
   копирования на 3024x1964/60 FPS. Android-текстура уже имеет независимые
   счётчики для проверки результата на конце цепочки.
2. Добавить отдельный SCK capture backend с проверкой доступности API и
   прежним fallback. Сохранить Idle-кадры, разрешения, курсор, дисплеи,
   смену размеров, сон/пробуждение и корректное владение CVPixelBuffer.
3. Отдельным изменением добавить прямой буферный путь в VideoToolbox.
   Сначала проверить существующие интерфейсы EncoderApi/EncodeInput;
   Apple-специфичное состояние не разносить по чужим платформам.
4. Не переносить настройки сервера, аккаунты, токены и другие изменения
   FastRustDesk: они не нужны захвату/кодированию и меняют протокол/семантику.
5. Проверить 60 FPS без увеличения очередей/задержки, CPU/температуру,
   несколько дисплеев, reconnect и совместимость с нашим сервером.

Публикация
AWDL и SCK/VideoToolbox — отдельные изменения после Android. Для теста на этом
Mac потребуется наша macOS-сборка и обновление app bundle вместе со службой.
Официальная установленная версия не получает новые возможности от одного
изменения Android или локального source tree. Бинарники/SDK/кеши в Git не идут.
